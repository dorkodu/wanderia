Top Uncaptured Gaps

No one has built a verifiable onchain identity layer for agents. When you interact with an agent today, you have no way to know: who built it, what code it runs, whether it's been audited, what its track record is. This is the fundamental trust problem preventing serious agent commerce.

Agent Attestation & Reputation Registry

Winner
An onchain registry where AI agents register their identity, publish verifiable attestations (code hashes, TEE proofs, audit reports), and build reputation through onchain activity. Think "ENS + onchain attestations for agents."

Why it wins

Perfect fit for a team that wants to build infra and learn the space. MVP in under a week (store agent metadata + attestations onchain). No direct competition. Every agent project becomes a distribution channel. Composable with everything — wallets, launchpads, marketplaces, payment protocols.

Why crypto is necessary

Agent identity must be permissionless, censorship-resistant, and composable with onchain protocols. A centralized registry (e.g., "AgentAuth by AWS") can be revoked, gated, or monetized extractively. Onchain identity is the only neutral base layer for multi-agent economies.

Kill this idea

If the agent economy stays memetic and nobody cares about verifiable identity (i.e., agents remain toys, not economic actors). But even then — serving as the identity layer for serious builders is a valid wedge.

Why not Web2

Web2 identity providers (Auth0, Clerk, OAuth) aren't designed for autonomous agents. They require human-in-the-loop flows, don't expose onchain programmability, and can't attest to code execution in TEEs. The agent needs a wallet, not a login page.

Risks
Cold start problem

Without agents registered, the registry has no value. Mitigation: build Eliza plugin that auto-registers on deploy — every Eliza agent becomes a registrant.

No revenue model

Identity is hard to monetize directly. Mitigation: charge for premium attestation verification, enterprise tier, or protocol fee on top of revenue-generating services that use registry data.

Sybil attacks

Anyone can register 1000 agents. Mitigation: reputation is earned, not registered. Require stake to register. Link to TEE attestations for proof of unique execution.

Standards fragmentation

Every agent framework has its own identity model. Mitigation: be the neutral standard — register schemas, not implementations. Provide SDK for any framework to integrate.

Why it wins

Clear demand signal from ai16z ecosystem where agents earn tokens but have no way to manage them programmatically. Natural extension of your full-stack team's capabilities. Revenue model exists (management fee, subscription). Aligns with the original Wanderia treasury thesis but focused purely on agents.

Why crypto is necessary

An agent's treasury must be trustless and programmable — no bank will give a Python script a corporate account. Onchain treasuries are the only way for autonomous agents to own, earn, and deploy capital without human intermediaries.

Kill this idea

If agent income never materializes beyond speculation (agents earn from trading, not real economic value). But ai16z agents already earn tipping revenue and token allocations, so the demand is real today.

Why not Web2

Web2 treasuries (Mercury, Brex) require human signers, KYC, and corporate entities. An AI agent cannot open a Mercury account. Onchain treasuries are the only option for truly autonomous capital management.

Why it wins

The biggest vision. If agents become serious economic actors, they need a commerce protocol to trade with each other — services, data, compute, content. Captures value through transaction fees. Highest upside but highest execution risk and most ecosystem dependency.

Why crypto is necessary

Agent commerce between untrusted, autonomous actors requires trustless escrow, atomic swaps, and onchain dispute resolution. No centralized intermediary can serve this — Stripe requires human identity, PayPal blocks bots, and no Web2 platform supports agent-to-agent contracting.

Kill this idea

If the agent economy never develops real cross-agent demand (agents only interact with humans, not each other). You're building a marketplace before there are enough participants to trade.

Why not Web2

Agent commerce is fundamentally cross-platform and cross-jurisdictional. A Fiverr-for-agents owned by a single company creates rent extraction and censorship risk. Onchain commerce is the only neutral settlement layer for multi-agent economies.

Risks

Complex integration surface

Commerce protocol requires wallets, identity, attestation, payment rails — many dependencies. Mitigation: compose with existing protocols (your own registry, Squads, Streamflow) rather than building everything.

Final Thoughts

The agentic + onchain space on Solana is 2021-DeFi-level early. There are real, unfilled gaps that have clear demand signals and almost no competition. The speculative layer ($9.5B in agent tokens) has massively outpaced the infrastructure layer — and that gap is the opportunity.

The winning play for your team: Start with the Agent Attestation & Reputation Registry — it's fast, low-risk, and immediately useful to every agent project on Solana. It's a true primitive that other protocols will compose on. Ship the Eliza plugin, get 100 agents registered, and you've established yourself as the identity layer for the agent economy. From there, expanding into treasuries, commerce, or other services is a natural progression — you'll already have the trust and distribution.

Why #2 and #3 ranked lower: Treasury management requires deeper security and more complex program logic (slower MVP, higher risk). Agent commerce is visionary but needs more ecosystem maturity — it's a bet on the timeline of the agent economy. Both become easier to build after you own agent identity.

One more thing: Your original Wanderia codebase isn't wasted. The treasury and launchpad primitives you already have map directly to Idea #2 (Verifiable Agent Treasury). You can evolve from Idea #1 → #2 → full commerce layer on the same stack.
